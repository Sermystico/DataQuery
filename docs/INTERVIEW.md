# DataQuery — Technical Interview Preparation & Architecture Deep-Dive

This document contains 15 concise, codebase-specific questions and in-depth answers detailing the design decisions, security engineering, database isolation, evaluation methodologies, and architectural trade-offs implemented in **DataQuery**.

---

### Q1: Can you walk through the lifecycle of a request through the DataQuery pipeline?
**Answer:**
When a natural language question is submitted to `POST /api/v1/query`:
1. **Middleware & Context**: `RequestIDMiddleware` generates a unique `req_<uuid>` and records start time.
2. **NL-to-SQL Generation**: `QueryService` invokes the configured `LLMProvider` (mock or Anthropic Claude 3.5 Sonnet) with a system prompt dynamically constructed from `schema_context.py` containing only the 5 allowed analytics tables.
3. **AST Policy Validation**: The generated SQL is parsed by `sqlglot` (PostgreSQL dialect) in `sql_validator.py`. It checks table allowlists, column allowlists, function allowlists, single-statement invariants, and strips comments. If valid, it returns an opaque `ValidatedSQL` token with normalized SQL and clamped `LIMIT 101`.
4. **Restricted Execution**: `query_executor.py` executes the `ValidatedSQL` strictly through the `readonly_engine` (`dq_readonly` role) within an explicit read-only transaction (`SET TRANSACTION READ ONLY; SET LOCAL statement_timeout = 3000;`).
5. **Formatting & Chart Detection**: `formatter.py` converts database types (Decimals to floats, dates to ISO-8601 strings) and produces deterministic `ChartHint` recommendations (bar or line) based on column types and cardinalities.
6. **Explanation Generation**: `explainer.py` sends query context and at most 20 actual result rows to the LLM. If the LLM explanation fails or times out, a rule-based fallback explanation is generated.
7. **Audit Logging**: `HistoryRepository` asynchronously logs the query, generated SQL, execution metrics, and status to `query_history` using the `app_engine` (`dq_app` role).

### Q2: Why is LLM output treated as untrusted user input, and what does this mean in code?
**Answer:**
LLMs are probabilistic token generators susceptible to prompt injection, jailbreaking, and hallucination. Treating LLM output as untrusted input means **no SQL string generated by an LLM is ever executed directly**. 
In code, this is enforced by:
1. `validate_sql(sql)` returns a strongly typed dataclass `ValidatedSQL(sql: str)`.
2. `execute_query(validated_sql)` strictly requires `isinstance(validated_sql, ValidatedSQL)`. Passing a raw string raises `TypeError("query_executor.execute_query() accepts only ValidatedSQL instances")`.
3. The constructor of `ValidatedSQL` is private to `sql_validator.py`. An attacker or unvalidated code path cannot bypass AST policy checks.

### Q3: Why use an AST parser like `sqlglot` rather than regular expressions for SQL validation?
**Answer:**
Regular expressions are fundamentally incapable of parsing context-free SQL grammars. Attackers bypass regex allowlists using:
- SQL comments (`SELECT 1 /* comment */ FROM ...`)
- String literals containing SQL keywords (`SELECT 'DROP TABLE' FROM customers`)
- Nested subqueries and CTEs (`WITH x AS (SELECT * FROM pg_catalog.pg_user) ...`)
- Case variations and whitespace obfuscation.

`sqlglot` parses the raw string into an Abstract Syntax Tree. We traverse AST nodes with `expression.walk()`:
- `exp.Table`: Extract table names and schemas, ensuring schema is strictly `"public"` and tables are in `ALLOWED_TABLES`.
- `exp.Column`: Check column names against `TABLE_COLUMNS[table]`.
- `exp.Anonymous` / `exp.Func`: Validate every function call against `ALLOWED_FUNCTIONS` (disallowing dangerous functions like `pg_sleep`, `pg_read_file`, or `eval`).
- Root node check: Verifies exactly one top-level statement exists (`exp.Select` or `exp.Union`).

### Q4: Explain the four-layer defense-in-depth model implemented in DataQuery.
**Answer:**
If any single layer is bypassed or misconfigured, the subsequent layers prevent compromise:
1. **Layer 1: Prompt & Context Sandbox**: The system prompt provides only the schema of 5 business tables. It explicitly forbids DDL, DML, and multi-table administrative queries.
2. **Layer 2: AST Static Analysis**: `sqlglot` inspects the AST before database execution, rejecting disallowed tables, functions, mutations, multi-statements, and system catalogs.
3. **Layer 3: PostgreSQL Role Isolation**: Execution connects exclusively as the `dq_readonly` user. Even if an attacker injects a `DROP TABLE` AST bypass, PostgreSQL rejects it at the database engine level with `ERROR: permission denied for table`.
4. **Layer 4: Transaction & Runtime Sandbox**: `SET TRANSACTION READ ONLY;` prevents state changes, `SET LOCAL statement_timeout = 3000;` cancels pathological runaway queries, and row limit clamping (`fetchmany(101)`) protects server memory from denial-of-service.

### Q5: How are PostgreSQL roles partitioned, and what principle of least privilege is applied?
**Answer:**
We configure three mutually isolated database roles in `scripts/bootstrap_roles.py`:
1. `dq_owner`: Schema migration and DDL owner. Owns tables in schema `public`. Used only by Alembic during migrations.
2. `dq_app`: Application user used by FastAPI for state management. Has `SELECT`, `INSERT` on `query_history` and `audit_log`, but has **zero access** to `pg_catalog`, administrative procedures, or DDL commands.
3. `dq_readonly`: Query execution user. Has `CONNECT` on `dataquery_dev`, `USAGE` on schema `public`, and `SELECT` exclusively on the 5 business analytics tables (`customers`, `products`, `orders`, `order_items`, `payments`).
   - `REVOKE ALL ON SCHEMA public FROM PUBLIC;`
   - Explicitly revoked from `CREATE TEMP TABLE`, functions, and system catalog mutations.

### Q6: Why did you configure two distinct SQLAlchemy connection engines?
**Answer:**
In `app/db/engines.py`, we construct:
- `readonly_engine`: Authenticates as `dq_readonly`. This is the **only** engine injected into `query_executor.py`.
- `app_engine`: Authenticates as `dq_app`. Used exclusively by `history_repo.py` to record execution audit logs.

This physical separation ensures:
1. Connection pool isolation: A spike in read queries cannot starve or deadlock application write operations, and vice versa.
2. Leak prevention: The execution dependency `get_readonly_engine()` cannot write to history tables, and the history dependency `get_app_engine()` cannot execute analytical queries.

### Q7: How does `query_executor.py` handle statement timeouts and runaway cross joins?
**Answer:**
Before executing any query, `query_executor.py` begins an explicit transaction and executes:
```sql
SET TRANSACTION READ ONLY;
SET LOCAL statement_timeout = {QUERY_TIMEOUT_MS};
```
If a query exceeds `QUERY_TIMEOUT_MS` (e.g. 3,000ms in production, or 100ms in resilience test `FAIL-06`), PostgreSQL aborts statement execution and raises error code `57014` (`canceling statement due to statement timeout`).
`query_executor.py` catches `sqlalchemy.exc.OperationalError`, detects the timeout error string, and raises a typed `QueryTimeout` exception, returning a clean HTTP 504 / JSON error envelope rather than hanging backend worker threads.

### Q8: Why are ground truth results calculated in Python instead of reference SQL?
**Answer:**
Testing SQL accuracy against reference SQL introduces circular dependencies:
- If reference SQL contains a semantic error or unhandled edge case (e.g. counting cancelled orders in outer joins), both the generated SQL and the test fail or pass silently together.
- In `eval/ground_truth.py`, all 32 golden query results are computed imperatively in pure Python using `seed.dataset.generate_dataset()`.
- Data is processed using Python dicts, list comprehensions, and Decimal math. This creates a true, independent oracle where SQL query results are validated against an entirely separate implementation domain.

### Q9: What is the negative control test in the evaluation suite, and why is it critical?
**Answer:**
A test suite that always passes is untrustworthy. In `eval/run_eval.py` and `backend/tests/evaluation/test_negative_control.py`:
- We inject intentional corruption into reference ground truth:
  1. Value corruption: Modify revenue from `1,259,220.88` to `999,999,999.99`.
  2. Column corruption: Change expected column `total_revenue` to `corrupted_column_name`.
  3. Row count corruption: Append an extra spurious row.
- The negative control asserts that `compare_results()` **must fail** with an `AssertionError`. This proves the evaluation comparator is strict, detects subtle regressions, and cannot produce false positive passes.

### Q10: How does DataQuery handle upstream LLM outages or garbage output?
**Answer:**
1. **Outage / Rate Limit**: If Anthropic API returns a network error or 5xx, `AnthropicProvider` maps it to `LLMUnavailable` (`app/core/errors.py`), returning HTTP 503 with a structured error envelope and user-friendly message.
2. **Garbage Syntax**: If the LLM generates invalid SQL or markdown gibberish, `validate_sql()` catches the parsing failure, marks `valid=False`, and records `"SQL syntax or tokenization error"`.
3. **Safety / Refusal**: If the question asks for unsupported data (e.g. employee salaries), the LLM generates `supported: false, reason: "..."`. The API returns `status="unsupported"` with the explanation, avoiding database calls.

### Q11: How does the explanation service guarantee factual fidelity without hallucinating?
**Answer:**
1. **Actual Results Only**: `explainer.py` passes the LLM only the question, column names, total row count, and at most the first 20 actual database rows.
2. **Deterministic Fallback**: If the explanation LLM fails, times out, or throws an exception, `explainer.py` catches the error and generates a rule-based template:
   - Single numeric value: `"The calculated {col} is {val}."`
   - Tabular data: `"Returned {count} rows for '{question}'."`
3. This guarantees that an explanation failure never fails an otherwise successful query execution.

### Q12: How are Docker images structured for minimal attack surface and production security?
**Answer:**
1. **Non-Root Backend**: `backend/Dockerfile` creates an unprivileged user `appuser` (UID 10001, GID 10001). The container runs without root privileges, preventing container breakout risks.
2. **Multi-Stage Frontend**: `frontend/Dockerfile` uses a Node 22 Alpine builder stage to compile TypeScript and Vite assets, then copies only the static `dist/` directory into a hardened `nginx:1.27-alpine` runtime image. Node and development dependencies are discarded.
3. **No Secrets in Images**: `.dockerignore` excludes `.env`, `.venv`, Git metadata, and sensitive caches. Secrets are injected at runtime via Docker Compose environment variables.
4. **Healthchecks**: Backend checks `/api/v1/health` via `curl`; frontend checks port 80 via `wget --spider http://127.0.0.1/`; PostgreSQL checks `pg_isready`.

### Q13: How does `backend/scripts/init_db.py` prevent data loss on container startup?
**Answer:**
In `backend/scripts/init_db.py`:
1. It polls PostgreSQL connection until ready (up to 30 retries).
2. It executes `alembic upgrade head` to ensure all migrations are current.
3. It executes `bootstrap_roles()` to ensure role privileges are locked down.
4. **Safe Seed Invariant**: It calls `get_existing_row_counts()`. If `sum(counts.values()) > 0`, it logs:
   `"Existing dataset detected. Skipping seed loading to preserve data."`
   It **never** runs `TRUNCATE` or `DROP TABLE` during automated initialization, ensuring existing operational data is never wiped.

### Q14: How does the React/TypeScript frontend mirror backend contracts and handle chart hints?
**Answer:**
1. **Strict Type Mirroring**: `frontend/src/types/api.ts` mirrors backend Pydantic models (`QueryResponse`, `ChartHint`, `ErrorEnvelope`, `HistoryItem`).
2. **Chart Hints**: Backend `formatter.py` produces `ChartHint(type="bar"|"line"|"none", x_key, y_key)`. The frontend `ChartView.tsx` automatically renders interactive Recharts bar or line charts when hints are present.
3. **AbortController**: `client.ts` wraps standard `fetch` with an `AbortController` timeout (default 15s), converting client-side timeouts or backend errors into user-friendly error banners.

### Q15: What are the main architectural trade-offs made in DataQuery, and how would you evolve it?
**Answer:**
1. **Trade-off: In-Memory SQL Parsing vs. Database EXPLAIN**:
   - *Choice*: Static AST parsing via `sqlglot` instead of PostgreSQL `EXPLAIN`.
   - *Rationale*: Zero database roundtrips for malicious queries, preventing side-channel attacks or denial of service on query parsing.
   - *Evolution*: Supplement AST parsing with read-only cost estimates (`EXPLAIN (FORMAT JSON)`) to reject queries with estimated cost > 10,000 before execution.
2. **Trade-off: Static Allowed Schema vs. Dynamic Tenant Catalog**:
   - *Choice*: Hardcoded 5-table schema allowlist.
   - *Rationale*: Zero risk of cross-schema leakage or unauthorized table discovery.
   - *Evolution*: For multi-tenant SaaS, introduce dynamic catalog providers keyed by tenant ID, storing allowed schemas in Redis and validating AST table nodes against the tenant's active schema partition.
